# v0.3 vehicle and enforced-constraint contract

This document defines the acceptance boundary for the v0.3 vehicle-validity
work. It is a contract, not proof that every item is implemented: a rule is
enforced only when the generated report marks it `active` and records its
result. Merely accepting, storing, or drawing an input field never counts as
enforcement.

## Release claim

The intended v0.3 claim is deliberately narrow:

> For the supported parking templates and vehicle classes, OpenParkCAD rejects
> layouts that fail its documented vehicle-maneuver checks or an active
> project-policy exclusion.

The claim does not establish statutory compliance, construction readiness,
traffic capacity, emergency-service approval, accessibility certification, or
fitness for a particular vehicle. Jurisdictional review and human CAD review
remain external release requirements.

## Rule authority

Every rule reported by v0.3 belongs to one of three authority tiers:

| Tier | Meaning | Solver behavior |
| --- | --- | --- |
| `advisory` | A diagnostic or optimization preference | May affect score or warnings; cannot be the sole reason for a hard pass claim |
| `project_policy` | A caller-supplied requirement for this project | Must be enforced when reported as active; failure makes the solve invalid |
| `jurisdictional` | A rule attributed to a named external profile | Must identify the profile and effective/source metadata; OpenParkCAD still does not certify legal compliance |

Absent authority metadata defaults to `project_policy` for explicit hard
constraints and `advisory` for optimization settings. A standards profile name
by itself does not activate jurisdictional rules.

Authority and execution priority are separate. `authority` records where a rule
came from; `priority` controls whether declared geometry is enforced. `hard` is
enforced, while `advisory`/`soft` can diagnose or score and `draw_only`/`future`
cannot contribute to a hard pass. Both should remain visible in reports. A
`jurisdictional` authority with `future` priority is still not active.

## Vehicle input semantics

Vehicle-level checks use `vehicles.design_vehicle`. The selected vehicle should
provide:

- `length` and `width`, in the top-level `units`;
- `wheelbase`, when the selected maneuver model needs it;
- `min_turning_radius`, interpreted as the minimum supported path radius under
  `turning_radius_reference` (`outer_front_wheel` or `rear_axle_center`);
- optional `track_width`, `front_overhang`, and `rear_overhang`, used when the
  selected reference convention or footprint model requires them;
- `swept_path_margin`, added around the simulated or audited vehicle envelope;
  and
- `max_reverse_distance`, the project-policy upper bound for the reported
  reversing portion of a maneuver.
- optional `configuration` (`rigid` or `articulated`), `hitch_offset`, and a
  nested `trailer` with length/width and optional wheelbase/overhangs.

A trailer object, or `configuration: "articulated"`, selects the articulated
path. Exact bicycle stall templates must not run for that class. A requested
`require_swept_path_check` fails closed with
`articulated_vehicle_template_not_supported`. Conservative analytic checks use
combination fit, steady-state trailer off-tracking versus aisle width, and a
tractor-arc-plus-trailer reverse bound; missing trailer geometry fails closed.

`constraints.maneuvering.require_turning_radius_check` and
`require_swept_path_check` are hard requests. A requested check must fail closed
when required vehicle parameters, geometry, or a supported maneuver template are
missing. Falling back silently to the older rectangular/L-shaped proxy is not a
passing v0.3 result.

The report should identify the vehicle, maneuver model/template version,
sampling or template tolerance, path length, reverse distance, minimum radius,
clearance result, and unsupported cases. Proxy results can remain available for
diagnosis but must be labelled `proxy`.

## Enforced geometry semantics

An exclusion affects the generated layout only when its report status is
`active`. Active exclusions are interpreted as follows:

- `site.obstacles`: obstacle geometry plus its declared clearance and applicable
  project setback;
- `site.reserved_areas`: hard no-stall/no-aisle areas according to their declared
  `affects` scope;
- `site_features`: feature geometry plus clearance, limited to the declared
  `affects` scopes such as `vehicle_clearance` or `stall_access`;
- `pedestrian_routes` and `accessible_routes`: protected route geometry for the
  affected stall, aisle, or swept-path scopes; and
- `fire_lanes`: protected access geometry for the affected scopes.

Geometry that cannot be interpreted must produce an explicit unsupported or
invalid-input result. It must not be discarded while the report claims that the
corresponding hard rule passed.

## Quota semantics

`parking.quotas.accessible_min` and `parking.quotas.ev_min` are minimum counts,
not score preferences. A quota is active only if the implementation can identify
qualifying stalls from the canonical stall-type `classifications` metadata and
can preserve that
identity in DXF/SVG/report output. An active unmet quota invalidates the solve.
Setting a quota to zero is a valid no-op; omitting it does not imply a statutory
default.

## Output and failure semantics

The final report should expose one vehicle/constraint validation block for the
exact official layout, including:

- contract and algorithm versions;
- active, advisory, unsupported, and failed rule lists;
- per-object conflicts with stable object identifiers;
- vehicle path/envelope provenance and tolerances;
- quota required/actual counts; and
- a single fail-closed `valid` decision.

Candidate previews may carry the same diagnostics, but a preview result cannot
stand in for validation of the promoted/exported layout. If any active hard rule
fails, the CLI must return non-zero and the transactional output set must not be
replaced.

## Representative regression corpus

Synthetic, representative real-site-shaped inputs live under
`tests/fixtures/v0_3/`. They intentionally contain irregular boundaries,
offset entrances, obstructions, and reservation geometry common in real design
work, but they are not surveys, customer sites, or evidence of field
validation. Each fixture carries provenance and intended invariants.

Before calling v0.3 complete, each intended invariant must be bound to an
automated report assertion or a documented human CAD review. Human comparisons
must record the reference tool/version, design vehicle, tolerance, reviewer,
and date. Test data alone does not satisfy that comparison gate.

## Acceptance checklist

- Requested vehicle checks fail closed when inputs or supported maneuver rules
  are missing.
- Swept-path and reverse-distance results belong to the exact exported layout.
- Active obstacle, reservation, route, feature, and quota policies reject
  violations.
- Report vocabulary separates `advisory`, `project_policy`, `jurisdictional`,
  `proxy`, and `unsupported` results.
- Representative fixtures have automated invariants and explicit synthetic
  provenance.
- Existing lint, branch-coverage, package-build, and installed-wheel smoke gates
  remain green.
- README and current-status claims match the report semantics without claiming
  statutory compliance or field validation.
